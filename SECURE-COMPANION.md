# Secure iPhone companion protocol

Porthole’s iPhone app and extensions require a matching PC build. The PC serves TLS 1.3 over IPv4 on ports 47731, 47732, and 47733 using the same persistent device identity. The phone verifies the exact SHA-256 digest of the DER leaf certificate on every connection. Publish the digest in the PC's pairing UI, with the address and pairing code. The QR format is `porthole://HOST:47731/CODE?pin=SHA256HEX`. Pairing and data require TLS.

The PC should generate a separate private key per installation, restrict access to it, and show a new QR if it is replaced. Bonjour is for finding candidate addresses. Its name, address, and TXT contents provide no identity proof. Rotate and time-limit the desktop's eight-character pairing code, rate-limit failed greetings, and store established phone credentials separately from the pairing code.

## Companion port 47731

Messages are UTF-8 lines terminated by LF, with binary bodies only after frame headers. The phone sends `HELLO TOKEN` inside TLS. The token is the eight-character pairing code for setup or the established 32-hex credential for reconnect. After authentication, reply `OK TICKET`, where TICKET is 64 lowercase hex characters from a cryptographic RNG. Optionally append a base64-encoded UTF-8 desktop display name as a third field. Keep ticket validity tied to the authenticated companion connection. Invalidate the ticket and close associated screen/inbox streams when pairing is revoked or replaced. Issue a new ticket on each new companion session. Compare secrets in constant time and keep payloads and credentials out of diagnostic logs.

Retain the existing `RESUME?`, `RESUME 2`, `PAIR CREDENTIAL`, and `PAIRED` exchange. A setup-code session can negotiate enrollment and submit `PAIR`. Its feature ticket and companion features become usable after the pairing is persisted. The phone stages its pending credential in Keychain before using the code and waits for `PAIRED` before publishing the verified pairing to the app and extensions. The PC consumes the code on durable persistence of the key in the current authenticated session. If the session ends first, the code stays usable until its original expiry. If the acknowledgement is lost after persistence, the phone can reconnect with its staged key. A repeated `PAIR` for the same authenticated phone and credential is idempotent. A reconnect retains the pairing and its transfer IDs and adopts a fresh session ticket.

- Advertise `SYNC READY` and `INPUT READY` after `OK`. Clipboard and managed input start disabled on every session. The phone sends `SYNC ID 0|1` and `INPUT ID 0|1 0|1`. The second input value restricts mouse and keyboard to screen sharing. Apply the corresponding preference before echoing `SYNC OK ID 0|1` or `INPUT OK ID 0|1 0|1`, with the exact command ID and values. The phone closes the session if the latest acknowledgement expires. Do not use the legacy bare SYNC or auto-enable input.
- Reply `IV READY` to `IV?` when the PC supports binding companion input to the current Bluetooth connection. An explicit verification action opens a focused phone screen before it sends `IV BEGIN ID`. The PC transmits a fresh 16-digit challenge through its Bluetooth keyboard connection. The phone submits those keypad events as `IV PROOF ID DIGITS` over TLS. The PC replies `IV OK ID` or `IV FAILED ID`. The phone sends `IV CANCEL ID` when that attempt is interrupted. Reset permission when the Bluetooth peer or companion session changes, or when controls are disabled. Send `IV RESET` if the companion session remains active. Check both verification and the acknowledged input policy before forwarding input. Keep challenge values out of UI and diagnostics.
- Use the existing `CLIP T BYTES` and `CLIP P BYTES` frames only while clipboard sync is enabled. `CLIP?` asks the foreground phone to read an explicit paste, subject to its pasteboard permission. Text is capped at 256 KiB and images at 8 MiB. `NAME DISPLAY-NAME` supplies the phone's local alias, as UTF-8 up to 40 characters, on the authenticated session.
- The phone advertises `FILES 2` and `FILES 3`. For a PC-to-phone file, send `PUSH2 ID SHA256 BYTES NAME` with a stable 32-hex transfer ID, content digest, positive size (512 MiB maximum), and valid filename. Wait for `OFFSET ID BYTES` before writing the remaining body bytes. `PENDING ID` means the phone is reserving or committing storage and can refresh the receipt timeout. `SAVED ID` is a durable commit receipt and can precede the offset on an idempotent retry. `NO ID` terminates the attempt. Keep the same ID, digest, size, and name across retries for that phone. Transfer one file at a time. With `FILES 3`, send `PUSH3 ID SHA256 BYTES NAME` with the same receipts as `PUSH2`. Frame each remaining body segment as `CHUNK BYTES` followed by exactly that many bytes, up to 64 KiB. Companion control and clipboard frames can appear between segments.
- For drag from Photos, keep the existing `PULL HASH ASPECT THUMB DETAIL [SCREEN]` request. Include a valid image preview for automatic matching. An explicit user selection can satisfy a valid request. The phone requests confirmation before any matched asset is exported. It replies `MISS [REASON]` or `FILE2 ID BYTES NAME` followed by exactly BYTES bytes. Save to a durable final location before replying `RECEIVED ID`. Reply `REJECTED ID` if the final save fails. Do not write another PULL request while a file or match is pending. The PC can send `CANCEL PULL` before publication. The phone cancels matching or approval and sends `MISS cancelled` when a file body has not started. If a body is in flight, the PC drains and discards it. The phone closes the companion connection if a restriction takes effect during an unframed body, so the PC can clear clipboard and input permissions immediately and apply current preferences on reconnect.

## Screen port 47732 and inbox port 47733

After TLS is ready, the first client line is `AUTH TICKET`. Match it to an active authenticated companion session and reply with exactly `OK\n` before reading any feature headers or accepting any data. A source IP is only a network address. Reject absent, invalid, and expired tickets. Re-read authorization when a connection is replaced. Prevent multiple concurrent writers from committing the same file transfer.

After authorization, keep existing PSCR framing and per-frame ACK bytes on 47732. On 47733, the phone uses PSHR 2 for resumable sends and PSHR 3 when its authenticated companion `INBOX?` request receives `INBOX 3`. Version 2 repeats the same transfer ID across interrupted attempts. Version 3 starts each item with `ITEM ID SHA256 BYTES NAME`. The PC scopes manifests to the stable pairing, verifies the digest before publication, and preserves the acknowledged final path. Both versions use `OFFSET BYTES`, `SAVED`, and tagged history stored independently of transient tickets. If the app or Share extension closes during a transfer, the phone retains its reviewed pairing, negotiated version, file IDs, and acknowledged items for retry in Connect. The app reuses those IDs and a fresh session ticket. A version 1 disconnect after sending bytes has an indeterminate result and needs user review before another send. Align port firewall rules with the TLS listeners and retain separate caps on connect, authenticate, transfer, and retry.

## iPhone signing and validation

Set `PORTHOLE_APP_GROUP` in Xcode to a provisioned App Group shared by the main app, Broadcast, and Share. Set `PORTHOLE_WIDGET_APP_GROUP` to a different provisioned group shared by the main app and Widgets. Use the same signing team and matching App ID capabilities for all four targets. A package that loses the companion entitlement during re-signing can pair in the main app, and Broadcast and Share will report shared pairing as unavailable. WidgetKit uses a generic snapshot when its group is unavailable. Run the signed checks in [NATIVE-VALIDATION.md](NATIVE-VALIDATION.md) against the matching secured PC build before distribution.
